# Clear to Trade — Product Prototype 详细设计

2026-09-08 · 设计审阅稿 v0.1 · 本轮未改产品代码、业务数据或 Customer Journey

## 先看结论

产品应围绕 **“我正在处理哪件工作，需要什么依据，现在能做什么”** 组织，而不是把批次、步骤、状态和技术说明逐层叠在页面上。

建议保留现有业务引擎、对象、权限守卫和返回合同，重组产品呈现层。第一张需要重新设计好的页面仍是 **Person T 筛查复核**：左侧看证据和差异，右侧处理当前问题，AI 的准备成果直接服务于这项工作。案件总览负责交代并行条件，不把每个工作台变成全案仪表盘。

本文先给出产品完整设计范围，再限定下一次可验证的制作切片；不是宣称全部页面已经实现。Customer Journey 的图片、流程和场景组织暂缓修改，只登记现有资产和后续接口。

### 本轮依据与证据强度

- **已确认设计约束：** Experience & IA v0.4、D5 v0.2、D4 总体分析及 Operating Model Brief v1.0。本文继承其业务边界，不把本次排版建议写成已批准需求。
- **本轮实际观察：** 两个现有产品入口、一页 PHKL 场景工作台的当前画面；截图见末尾。没有操作查询、保存、提交、批准或重置。
- **代码核对：** Product Experience 外壳、进度投影、场景媒体宿主、流程图与 D4 资产入口。
- **历史完成情况：** 既有 D4/D5 交付报告可说明当时的试点范围；其中历史测试数字不作为本轮测试结果。之后 A–F 引擎与页面有其他增量，不能据旧报告断言这些业务能力不存在。
- **PPT 对应：** 本文沿用 D5 已有 SCN → PX → M/C 引用；本轮没有重新逐 shape 审核 PPT，最终 Journey 对齐时另做原件复核。
- **PHKL：** 只借鉴场景表达与视觉导航，不引用其医疗规则、角色权限或发布门禁作为银行事实。

## 1. 当前版本为什么不像一个连贯的产品

| 当前发现 | 实际依据 | 对使用者的影响 | 本次设计处理 |
|---|---|---|---|
| Population 页也显示 Screening Review 与六组命中复核步骤 | 截图 1；`productWorkspaceHtml` 固定内部标题，`productProgress` 构造 MATCH 步骤 | 用户分不清正在定义筛查范围还是处理疑似命中 | 按工作类型装配页面；Population 与 Finding Review 有各自问题、步骤、动作 |
| 当前展开状态下，六组责任/时间详情占据主体上方 | 截图 1，AX 记录中多组 Unknown / Not recorded；代码顺序为定位→进度→任务 | 看了许多状态，仍未看到需要判断的证据 | 保留紧凑进度摘要，详情在当前工作之后或就地展开；不移除必要状态 |
| 直接进入的页面要求先理解 Batch B/C 和初始化 | 截图 3 | 没有清楚的正常产品起点，容易被理解为“点了没有反应” | 有会话就恢复精确任务；无会话先明确选择合成案例，再打开任务；演示设置不伪装成银行操作 |
| 外层角色投影、批次提示、模拟返回结果选择与正常工作并列 | 截图 1/3 与页面 AX | 演示机制比业务动作更突出 | 演示工具收进外层工具区；正常工作保留真实字段、证据、动作和回执 |
| AI 的价值主要是独立分工说明，未在已观察首屏形成可用成果 | 截图 1；D4/D5 来源和现有模块 | 用户看到技术概念，却看不到具体少做了什么准备工作 | 把带出处的比较、缺口清单、复核包和下一工作建议放进任务 |
| 图并未全部消失，但入口分散、部分位于折叠层或另一个工作室 | `app.mjs` 高层流程 details；Product 的 OPT-DEPENDENCIES；媒体宿主与 D4 manifest | 现有视觉资产难以构成连续理解路径 | 区分默认可见的必要关系图与按需的完整说明图，见第 9 节 |

以上是**有界检查**，不是“所有页面完整 UX 审计”。截图 1 的展开状态可能来自保存偏好，不能称为所有用户的默认状态。问题在于展开后仍把整套明细排在真正工作之前。

## 2. 产品框架：两种入口，一个案件上下文

### 2.1 直接进入产品

有有效会话：恢复最近处理的获准工作，保留案件和草稿。首次进入：展示一个简洁的合成案例入口，说明 Entity A 申请 FX forward；用户明确打开后进入案件概览。选择示例不得覆盖未保存工作或悄悄导入成功结果。

案件概览回答四件事：

1. 申请的主体与范围是什么；哪些仍待确认。
2. 当前角色可处理的工作是什么；每项只有一个明确入口。
3. 哪些工作在等别人，具体等什么、由谁跟进。
4. 为什么目前不能确认准入；点击阻塞直达关联任务。

不做企业级 Dashboard、排行榜、虚构 KPI 或全案完成百分比。

### 2.2 从 Studio / Operating Model 进入

直接打开同案、同对象的工作，不能先绕案件首页。没有匹配任务时保留来源，说明“当前会话尚无此复核任务”，给出已有的前置工作入口；需要另开合成示例时必须显式选择。

Product 始终表达 Target 工作方式。来源可以是 Current；返回仍恢复来源 Current，不把全局比较状态改成 Target。

### 2.3 页面空间层级

| 空间 | 放什么 | 不放什么 |
|---|---|---|
| 外层演示栏 | 返回来源、语言、合成环境标记、演示设置 | 银行业务批准、假身份认证 |
| 产品导航 | Cases、当前案件 Overview、工作与对象入口、History | Batch A–F、D4 分数、Agent/Skill 目录 |
| 紧凑案件定位 | Entity A · FX forward；当前任务；Owner/下一责任方；当前状态 | 三行完整版本号、源码路径、整案全部时间表 |
| 主工作区 | 当前问题、必要依据、当前角色操作 | 装饰性营销图、完整方法论 |
| 关联详情 | 原始引用、完整流程、Activity、历史、非必要资料 | 隐藏决定所必需的原依据或关键阻塞 |

导航名称沿用现有产品概念，不新建一套业务 ID。桌面可使用克制的左侧案件导航；进入聚焦任务后，顶部保留返回案件与精确任务标题。有限 Client 入口使用独立简化投影，不展示内部菜单的灰色禁用版。

## 3. 同一案件，不同角色看见不同工作

以下是**产品视角**，不是新的银行组织架构或权限结论；具体 ROLE ID 和允许动作沿用已有配置。

| 视角 | 默认工作 | 必须看见 | 主要动作方向 | 不得默认获得 |
|---|---|---|---|---|
| Case Manager / KYC Operations | 当前任务与案件阻塞 | 要求、缺口、用途评估、交接、影响范围 | 准备请求、评估指定用途、协调或移交 | 所有专业判断和最终准入权 |
| Relationship Manager | 客户请求与可解释进展 | 请求原因、获准收件人、等待对象、下次更新 | 审阅客户措辞、协调、保存/复制邮件草稿 | 受限名单叙事、冲突调查、豁免要求 |
| Client contributor | Your tasks | 为什么找我、具体需要什么、用途、本人回执 | 保存、提交指定资料、回应指定问题 | 整案资料、其他人的信息、自动代表或签约权 |
| Screening reviewer | 指定 Finding | 原查询、识别信息比较、必要证据、未知与矛盾 | 补件、转交、保持未决；配置允许时记录处置 | 永久白名单、全案准入 |
| Financial Crime / EDD | 指定风险问题 | 适用依据、风险问题、材料与升级条件 | 专业评估或配置允许的决定 | 因未演示就将 EDD 设为不适用 |
| Credit | 当前信贷条件 | 初次决定、条件内容、履行状态、Legal 使用版本 | 已有范围内的条件审阅/记录 | 把条件批准等同条件已履行 |
| Legal | 当前协议工作 | 协议版本、Credit 输入、签字权限、执行状态 | 已有范围内的协议处理 | 将草稿、批准与已签署合并 |
| Conflicts / Control Room | 获准范围的搜索与复核 | 相关性、hold 范围、受限移交 | 指定专业复核与局部结果 | 向 RM/客户泄露调查内容 |
| QA reviewer | 具体缺陷与重审 | 检查范围、缺陷对象/用途、补正、当前版本 | 指派补正、重审、配置内签核 | 补正完成即自动 QA 通过 |
| Clearance reviewer | 当前范围的确认任务 | 清单完整性、所有适用条件、hold、QA 与版本 | 有权确认；与发布分别处理 | 未配置的权力、实际交易执行 |

**Person T 的特殊限制始终可见：** B 的任职资料只是与 B 的关系信息；协调 A 的声明不等于 A 的确认授权。协调、签署、交易指令和系统访问分别核验。没有有效有限 Grant 时，Client 页面只提供安全解释与 RM 联系路径。

## 4. 十二种工作模式的详细页面合同

PX 为 D5 已有展示模式，不是十二套系统。建议最终统一呈现层；下一次实现只选第一条切片，不同时精修全部页面。

| 模式 / 现有场景 | 默认内容与信息组织 | 最小真实动作及输出 | 必须保留的边界 |
|---|---|---|---|
| **PX-01 案件概览与 Tasks** | 顶部申请范围；中央当前角色可行动任务；下方并行条件摘要与阻塞；History 固定可达 | 打开精确任务、查看只读历史；浏览无业务写入 | 无清单完整依据不报全案百分比；本人工作完成≠案件归档 |
| **PX-02 Scope / Parties / Authority** · SCN-SCOPE/ENTITY | 左侧申请范围；选主体后看关系图、原声明与用途权限；每条关系有来源状态 | 现有受控 Scope 编辑、主体/关系与权限审阅记录 | reported parent 不等于已验证所有权；B 雇佣 T 不等于 T 可代表 A |
| **PX-03 Requirements / Evidence** · SCN-REQUIREMENTS/SOURCE | 要求优先列表：针对谁、为何适用、需要何种证据、可复用什么、剩余缺口 | 打开来源、关联候选资料、按现有命令准备请求 | Unknown 不静默排除；找到/关联资料≠该用途已满足 |
| **PX-04 内部 Requests** · SCN-GAP | 按缺口逐项组织：用途、请求内容、收件人、可披露性、访问范围、审阅状态 | 保存草稿；单独审阅与模拟派发；产生版本与回执 | 草稿不发送；不同用途的新请求不扩大旧 Grant |
| **PX-05 RM Client requests** · SCN-GAP | 左侧请求与等待列表；中央客户可理解摘要；邮件草稿为可选模块 | 编辑/保存/复制草稿、协调记录；派发仅用既有守卫入口 | 默认 Email 联系；Copy≠Sent；不能向客户引用内部合成 SLA |
| **PX-06 Client Your tasks** · SCN-GAP | 独立简化页面；请求原因、各项要求、文件/回答、提交回执 | 有限 Grant 内保存/提交指定项目 | 上传成功≠接收安全放行≠用途充分；不显示内部 Finding 详情 |
| **PX-07 Evidence Review** · SCN-VALIDATE/SOURCE | 文档预览和原文位置；候选 Claims；主体、来源、用途；逐用途评估 | 通过现有安全接收条件后记录用途评估、反馈精确缺口 | 不用单一“文件已验证”覆盖所有用途；技术失败不等于证据不真实 |
| **PX-08 Population / Coverage** · SCN-POPULATION | 主体清单与包含依据；尚未明确的关系；查询计划与逐次结果；覆盖限制 | 准备/请求初步查询，接收独立模拟返回，再核对覆盖 | 查询失败≠零命中；查过部分名字≠完整适用覆盖 |
| **PX-09 Screening Review** · SCN-MATCH | 身份对照、原证据、准备好的复核包、人工行动区；详见第 5 节 | 精确补件、转交、保存草稿、有权且有据的局部记录 | 不自动排除；复核包≠决定；局部结果≠全案准入 |
| **PX-10 Condition Detail** · EDD/CONFLICTS/CREDIT/LEGAL | 共用“当前问题—依据—条件—等待—动作”容器，按专业领域装配字段和局部图 | 复用已批准且实际存在的 D2 专业命令；未绑定动作明确只读 | 专业过程不能简化成四张通用 Approved 卡片；不新增完整审批系统 |
| **PX-11 QA Remediation** · SCN-QA | 具体检查项、对象/用途/版本、缺陷类型、负责补正者、重审 | 精确分派、补正交回、独立重审/配置内签核 | 缺用途评估可能需要银行补做评估，不默认再次向客户要文件 |
| **PX-12 Clearance** · SCN-READINESS/PUBLISH | 当前范围→条件完整性→就绪依据→有权确认→各目标发布回执 | 既有确定性计算、独立确认记录、独立模拟发布与反馈 | Ready≠已确认；确认≠已发布；发布失败保留决定；不执行交易 |

每种页面都需定义：读取对象、可见投影、当前输入版本、唯一主动作、允许命令、产物引用和回点。未完成接线的入口不得跳通用 Screening 页冒充对应工作台。

## 5. 第一张精修页面：Person T 的 Screening Review

### 5.1 首屏应让人立即看懂什么

标题：**筛查复核 · Person T**。下一行是 Entity A / FX forward 与任务状态。当前问题直接写成业务语言，例如“现有信息不足以区分 Person T 与名单记录”；只在当前合成数据确实支持时使用该措辞。

保留一行 Owner、下一行动方、进入/等待时间与预计说明。没有记录时集中表达“开始时间未记录；预计待资料完整后确认”，不把每个缺失时间戳各占一行。未定 Owner 仍显示未分配及需要由谁确认，不隐藏责任缺口。

桌面主工作区采用稳定的**约 2/3 依据区 + 1/3 行动区**。不是右侧弹出抽屉，也不是先看几屏步骤说明才能操作。

### 5.2 左侧：依据区

1. **身份比较表。** 每行一个可比较属性；两列分别为 Person T 与 provider record；另列显示来源/精度、相同/不同/无法判断。只显示真实合成输入拥有的属性，不补生日、国籍或 ID 来制造可比较效果。
2. **原始证据。** 点击比较项，在同页证据区域定位原资料和页/段；保留文档版本、收到时间、来源、具体用途评估。无文件预览时提供可读摘录与来源说明，不能用虚构扫描件充当银行证据。
3. **准备好的复核包。** 分为已有事实、未知/矛盾、缺口建议、允许出口。每个有影响的判断候选可追溯到输入；“AI 准备”与“人工已记录”使用不同标签和容器。
4. **必要关系提示。** Person T—Entity B—Entity A 的关系/authority 摘要在影响本项工作时直接可见；完整关系图按需打开，但关键“尚无 A 特定用途权限依据”不藏在图里。

### 5.3 右侧：当前行动区

默认展示具体问题、尚缺依据、当前角色允许动作和预期影响。正式处置不预选，不把“排除疑似命中”作为默认绿色成功出口。

| 当前状态 | 主动作 | 次动作与必要提示 |
|---|---|---|
| 资料不足、允许组织补件 | 准备资料请求 | 保存复核草稿、转交；说明请求针对哪项身份区分用途 |
| 请求待内部审阅/派发 | 审阅当前请求或打开对应工作 | 不把请求草稿说成已等待客户 |
| 有效请求已派发、等待回应 | 查看请求与等待状态 | RM 跟进；不反复生成重复请求 |
| 新资料收到、尚未可用于判断 | 评估本次资料用途，或处理明确的接收前置 | 明确区分技术接收、主体关联、用途评估 |
| 资料已按用途审阅，当前角色有权 | 审阅并记录本项结果 | 理由、引用、当前输入版本必填；允许保持未决或转交 |
| 当前角色无权或配置未明确 | 查看材料 / 转交配置允许的角色 | 明示欠缺权限配置；不显示可误点的 Approve |
| 输入版本发生变化 | 核对变化 | 保留草稿；过时结论不能提交 |
| 局部决定已记录 | 查看本项影响 / 打开下一工作 | 显示仍开放的 Coverage、ownership、Legal 等实际条件，不庆祝全案完成 |

保存草稿为次级动作。正式记录前就地确认对象、用途、结论、依据和有限影响；出现错误留在原表单，保持输入。结果回执替换行动区的状态，而不是只有一个短暂 toast。

### 5.4 进度与流程怎么呈现

页内保留 D4/D5 既有六组，但默认只用紧凑位置条；选中组显示其责任、时间、输入和允许动作。查看未来组只是阅读，不推动业务。当前真正工作与当前查看组不同的时候，直接写明。

“按需补证”是分支，不是每案必经第三步；额外批准仅由既有 demo config 决定。完整 Archify 协作图放在“本项工作如何衔接”区域，当前人机移交点有静态摘要；不能依赖播放才能理解。

### 5.5 同案闭环

打开 Finding → 检查资料 → 为具体缺口建立请求 → RM 审阅/协调 → 有限 Client 提交 → Ops 接收与用途评估 → 有权 Reviewer 判断或保持未决 → 查看局部影响与全案剩余条件 → 返回原场景。

每个箭头代表有实际条件的交接，不代表 Next 按钮。客户回应与人工判断必须通过相应本地受控动作发生；演示后续故事只能进入标明为只读的作者检查点。

沿用 CHK-01 至 CHK-04（资料不足、收到未评估、用途已审阅、局部记录）的既有设计身份。检查点必须先映射真实已批准 fixture；缺权限或成功结果时保留未决，不为截图补一个通过结局。

## 6. AI Agentic：产品中出现什么，后台边界是什么

### 6.1 不把所有自动处理都叫 Agent

| 执行方式 | 本产品负责的工作 | 用户看见的结果 |
|---|---|---|
| 确定性规则 / Workflow | 版本、权限、来源资格、查询回执、依赖与 readiness 求值、记录/发布守卫 | 清楚的检查结果、失败原因、可行动作；不是一个 AI 推理故事 |
| 有范围的 Skill | 字段提取候选、属性对照、复核包、带引用摘要、请求草稿 | 可检查、可修改的准备成果；不作为正式业务判断 |
| Bounded Agent 候选 | 获准路径存在不确定分支时，有限规划下一次取证或下一工作建议 | 计划、依据、已允许输入/工具范围、停止原因与待人工问题 |
| Human | 权限/披露确认、专业判断、必要批准、正式处置 | 可审阅的决策包、允许出口、有限后果和正式记录 |

现有 D4 是**两个主要候选 + 一个条件候选**，不是已经运行的多 Agent 平台。当前本地原型没有真实模型调用或银行集成；“预编制示例”“本地规则模拟”“真实模型运行”必须分别标明，最后一类本轮不存在。

### 6.2 三个 Agent 候选合同

| 候选 | 目标与允许范围 | 产品产物 | 停止与人工接手 | 禁止事项 |
|---|---|---|---|---|
| **AG-CASE** · 案件工作规划 | 读取当前 scope、已知依赖、可行动工作；提出有限下一工作顺序 | 有依据的待办建议，说明为什么先做、哪些可并行 | Scope/版本变化、权限未知、必要数据缺失、无进展或预算边界 | 不降低条件、不修改银行优先级规则、不决定 Ready，不创造批准 |
| **AG-EVID** · 证据协调 | 仅在获准来源内选择下一取证方向，整理缺口与用途候选 | 来源计划、引用、候选 Claims、缺口列表、请求草稿 | 来源/访问/用途不明确、重要矛盾、预算或循环上限、人需判断 | 不扩大访问、不宣称资料充分、不派发请求、不确认主体或 authority |
| **AG-REVIEW** · 自适应复核准备（条件候选） | 当前 Finding 的身份区分准备；只在路径需适应结果时考虑 | 对照与复核包、待询问问题、停止原因 | 身份歧义、重大性、升级、权限/hold 条件 | 不排除命中、不批准 EDD、不解除 hold、不准入 |

AG-REVIEW 可能复用 AG-EVID 的隔离任务模式；只有独立上下文、质量评价和责任边界确有需要时才独立。共享能力不等于共享访问权。若固定来源顺序已够用，采用 Workflow + retrieval，不为了展示 Agent 增加自主循环。

### 6.3 沿用原 Skill 家族，不新建编号

| 工作 | 原 Skill | UI 的正常业务名称 |
|---|---|---|
| 上下文/获准来源、候选提取、属性比较 | SK-01 / SK-02 / SK-03 | 来源与资料、提取内容、信息对照 |
| 范围条件与证据用途准备 | SK-04 / SK-05 | 适用要求、用途检查 |
| 包编写与工作路由 | SK-06 / SK-07 | 复核材料、待处理工作 |
| 客户协作与接收 | SK-08 / SK-09 | 请求草稿、资料回执 |
| 依赖求值、记录与投影发布 | SK-10 / SK-11 / SK-12 | 条件核对、处理记录、获准发布状态 |

完整能力矩阵与执行选择理由留在 Studio 的 Operating Model。产品主屏不展示 SK 编号、D4 评分或部署目录；必要审计引用从“依据与记录”进入。

### 6.4 AI 成果卡的字段与交互

建议组件名称使用“已准备的复核材料”“建议补充的资料”，不要统一叫“AI Assistant”。字段来自现有对象和来源引用；以下是展示合同，不是第二套业务 store。

- **产物与用途：** 为哪个任务/主体/用途准备了什么。
- **事实与出处：** 可定位的资料引用、输入版本、原文精度；明确区分提取候选与已记录判断。
- **未知/矛盾：** 哪些无法确认、为什么影响当前动作。
- **准备方式：** 本地规则、预编制 Skill 示例或 Agent 候选示例；不显示假的“实时分析中”。
- **建议与替代：** 建议下一动作及依据；固定流程足够时说明无需 Agent。
- **等待人工：** 问题、需要何类判断、哪些选项有权采用。
- **当前有效性：** 输入是否变化、哪些部分需重新核对。
- **允许交互：** 查看出处、修改草稿、保存草稿、打开真实受控任务。点击采纳建议不隐含发送或批准。

普通证据表无需加一枚 AI 图标到每一行。对用户重要的是内容可查、可纠正、可用于下一项工作，而不是模型存在感。

### 6.5 人机交接合同

需要人时，原工作区就地出现决策包：**为什么暂停 → 正在问什么 → 当前事实/未知 → 允许选项 → 每个选项的影响 → 谁有权 → 记录后能恢复什么**。

人可以要求更多资料、纠正候选内容、转交、拒绝建议或在允许范围内记录结果。正式记录后，系统重新核对当前 Case/Scope、证据/查询版本、权限和 hold，再恢复确实被该结果解除前置的工作。其他独立分支是否继续由真实依赖决定。

播放结束、超时、阅读材料、切换角色、点击 Next 都不能触发恢复或批准。发生输入变化时保留旧包为历史，提示需要重审；不静默重跑后覆盖人的理由。

## 7. 字段、状态与写入合同

### 7.1 继续使用 Shared Case Spine

Case、Scope、Entity、Representative / Authority、Requirement、Evidence、Evidence Use Assessment、Work Item、Dependency、Screening Finding、Decision、Clearance Condition、Readiness Snapshot、Audit Event、Story Route 继续是既有对象。正式字段名、command 名与 ref 从仓库绑定读取，不以本文中文名称创建重复 schema。

| UI 内容 | 数据来源/关系 | 写入边界 |
|---|---|---|
| 案件定位 | Case + 当前 Scope + Work Item/Finding 引用 | 导航只保存引用，不复制业务快照 |
| 身份对照 | Entity/Representative、query/result、Evidence/Claims | 候选比较不是身份确认 |
| 资料可用性 | Evidence + 针对主体/用途的 Assessment | 文件收到不批量满足所有要求 |
| 下一动作 | Work Item + 当前 Dependency + 角色投影/权限判定 | UI 不能自行放宽 disabled 条件 |
| AI 准备包 | 既有 draft/pack、source refs、input revisions | 建议只形成草稿或受控命令意图 |
| 人工结果 | Decision + actor/authority basis + 当前输入 + Audit Event | 理由、范围、版本与权限校验后才记录 |
| 全案状态 | 当前适用条件清单 + completeness + holds + freshness | 确定性求值；无完整清单不能空集 Ready |
| 页面偏好 | persona + role + workspace + layout version | 仅布局数据，不影响要求、授权或任务顺序 |

### 7.2 状态不合成一盏红绿灯

- **工作状态：** 尚未开始、处理中、等待、当前动作受阻、局部完成。
- **时间健康：** 有目标/依据才显示按计划、需关注、超过已确认时限；没有 SLA 就不报 SLA breach。
- **下一行动：** 动词 + 对象 + 责任方；Owner 与下一行动方可以不同。
- **新鲜度：** 当前、旧版本需重审、未知。
- **全案准入：** 单独依据条件求值和有权确认，不从步骤颜色推断。

未知集中展示为可处理的问题，不重复刷屏，也不能隐藏。例如“尚未确认 B 的关系及适用覆盖；需要完成群体范围复核”，优于连续多个裸露 Unknown。该表述只能在数据确实对应时使用。

### 7.3 时间与历史

首层显示当前任务进入时间、等待对象/起点、有依据的预计或未能预计原因。完整事件时间表按需查看。打开页面不产生开始事件；状态驻留不是人工净工时；并行时长不简单相加推算准入日。

History 分为进行中、我的已处理工作、获准归档。历史快照只读、时间冻结、按当前权限过滤；没有已批准的结果 fixture 就明确没有此样例，不用空壳历史制造成熟产品感。

## 8. 完整交互状态与视觉规范

| 状态/动作 | 页面响应 | 必须验证 |
|---|---|---|
| 默认 / 悬停 / 按下 | 默认静止；可操作控件轻微上浮/按压；图形和阴影同步 | 非交互标签不表现成按钮；不依赖 hover 才读必要内容 |
| 键盘焦点 / 选中 | 清楚焦点框；选中态不仅靠颜色；Tabs 有连续明确的位置反馈 | Tab 顺序、Enter/Space、关闭后焦点回源 |
| 禁用 | 禁用对象与原因在附近可读 | 无权限、无输入、过时、加载中分别解释 |
| 保存中 / 成功 / 失败 | 防重复提交；持久回执；失败保留输入与错误 | 不能只有 toast；未存不假称完成 |
| 未保存离开 | Save draft / Discard / Stay | 保存失败不导航；丢弃仅本次草稿，不撤销已记录事实 |
| 语言切换 | zh-CN / en-AU / en-US，保留任务、表单、语义位置 | 不更改政策、时区依据或数据；返回使用最新语言 |
| 来源/文件不可用 | 保留引用、文字替代和明确缺失范围 | 不伪造证据预览；必要依据不可用时限制正式动作 |
| 窄屏 / 触屏 | 依据先、行动后；主动作保持可达；复杂对照有可访问横向容器 | 触屏按下/松开反馈，不需要 hover；不裁掉结论依据 |
| 减少动态效果 | 关闭倾斜、拉伸、弹性与自动播放 | 静态仍能理解选择、交接和结果 |
| Print | 选定工作完整内容、必要依据、来源/版本、局部后果 | 不只打印 viewport；按角色过滤；示例标识保留 |

**视觉方向继承用户已经确认的黑 / 蓝 / 白，不出现紫罗兰或薄荷青。** 暖米灰环境、炭黑导航、白色高可读工作面，蓝色集中用于主动作与选择。玻璃只用于外层壳、轻量工具条和少量操作层；文档/表格/输入使用稳定乳白或白底，避免所有卡片同等发光。

建议后续测量目标：正文与表格常规 15–16px、主任务标题约 28px；技术追溯 12–13px 且维持可读对比度。小字与折叠用于次级 ID，不用于掩盖关键业务限制。触屏关键操作目标建议不小于 44px。

材质描述准确：**backdrop blur + 渐变高光/阴影模拟**，不是实际光学折射。不增加全屏强模糊、霓虹、漂浮背景或持续呼吸效果。

| 人机边界 | 引用可查、建议可改、人工可保持未决、无越权恢复 | 待新界面回归 |
| 状态安全 | 零命中/失败/不完整、收到/充分、局部完成/准入分别验证 | 待新界面回归 |
| 导航与草稿 | Current 返回、精确回点、语言不回滚、Save/Discard/Stay | 待新界面回归 |
| 权限 | Client 只读获准项目；角色投影不被声称为生产认证 | 待新界面回归 |
| 可读与无障碍 | 桌面/窄屏/键盘/触屏/减少动态效果；必要依据始终可达 | 本轮只有桌面截图，不声称全部通过 |
| 图片/图/打印 | 缺图仍可理解；打印完整选定工作而非 viewport；媒体零业务写入 | 待新界面回归 |

建议审阅者按同一案件完成一次任务走查，分别记录“找不到”“看不懂”“不能做”“结果不明确”。功能测试通过不自动证明产品体验良好；未验证项明确记 not-run。

## 13. 待确认事项与默认建议

1. **产品进入方式：** 建议保留直接恢复任务 + 薄案件概览两种入口，不强制看 Dashboard。本文按此设计。
2. **AI 表达：** 建议本次继续做可追溯的合成准备成果和受控工作，不接真实模型；任何真实 Agent 试验另需来源权限、工具范围、成本/停止条件与评价授权。
3. **银行未知项：** 专业权限、额外批准、可用来源、SLA 和外部披露均沿用未决项；无法明确的动作解释限制，不由 UX 文案补政策。

下一项需要共同审阅的是 **第 5 节筛查复核工作台**：信息够不够、AI 成果是否有用、人工判断是否清楚。通过后才制作该切片，再处理 Journey。
