```bash
cd "experiments/customer-journey-optimised" && python3 build.py
```

```bash
python3 -m http.server 8879 --bind 127.0.0.1 --directory "experiments/customer-journey-optimised/output"
```

Re-import the workbook only when it changes. **The source `.xlsx` is not in the repo** — it was read from `~/Downloads` and is no longer there. `workbook.json` is the retained copy of its content and `build.py` reads that, so the page builds fine without it; you only need the spreadsheet to pick up changes:

```bash
cd "experiments/customer-journey-optimised" && python3 import-workbook.py "/path/to/Clear_to_Trade_Scenario_AI_Feature_Research_Mapping.xlsx"
```

`import-workbook.py` fails with that explanation if the path is wrong, rather than a stack trace. **Worth doing:** drop a copy of the workbook into `00_sources/raw/` so the lineage stops depending on a Downloads folder.

Regenerate the process CSVs from the PPT — **copy any filled-in versions first, this overwrites all three**:

```bash
cd clear-to-trade-product && python3 scripts/extract_process_map.py
```

The 24 images were resized once with macOS `sips`; the command is recorded in `JOURNEY_OPTIMISATION.md` §5. They do not need regenerating unless the source assets change.

## 3. Data lineage — what is grounded in what

This matters more than the file list. Three tiers, and the page states them on itself.

### Extracted fact (machine-read from `Sanitised Process Map.pptx`, SRC-007)

- All node IDs, titles and stage groupings, M0.1–M8.5 and C1.1–C2.7.
- **Swimlane membership**, read from shape geometry against the lane-label positions — not from looking at the picture.
- The client-lane touchpoints and their x positions, which is how each one is assigned a process column.
- Which shapes exist in the current map and not the target, and vice versa.

### Derived hypothesis (ours, marked as such, awaiting confirmation)

- **Delta type per node** in `before_after_delta.csv`. Geometry tells us a node moved lane; it does not tell us the move was deliberate.
- **Scenario → process anchor and column span**, in `output/scenario-process-anchors.json`. SRC-007 numbers activities; the R03 scenario layer carries no M/C ids, so the ranges printed on every scenario block are our reading.
- **The eight client touchpoints' experience fields** — what they see, wait for, and find difficult — in `client-journey.json`. The *task statement* of each is SRC-007 shape text; everything around it is inference.
- **The opportunity line on each client touchpoint.** These are our proposals and are not in the source at all.

### Third-party analyst content (reproduced verbatim, not client-validated)

- Pain points, opportunities, the six 1–5 scores, recommended direction and control boundaries, from `Clear_to_Trade_Scenario_AI_Feature_Research_Mapping_v0.1.xlsx`. The workbook marks these `DESIGN_HYPOTHESIS_NOT_CLIENT_VALIDATED`.
- The 28 references, with what we borrow and the boundary on using each.
- **The pain and opportunity text is Chinese**, because the workbook is. It is reproduced word for word — nothing translated or reworded — while the rest of the page is English. See §6.

### Not present at all

No durations, no SLA, no KPI, no completion percentages. None are sourced, and the design system forbids inventing them. Waiting is expressed as *who* and *what*, never *how long*.

## 7. Known limitations

Stated plainly so nobody inherits a false impression.

- **Nothing is client-validated.** Every pain point, score, persona trait and journey moment is a hypothesis. The workbook says so; the page says so.
- **The scenario → process mapping is unconfirmed.** It appears on every scenario block and in the panel header, so if it is wrong it is wrong in a visible place. Check `scenario-process-anchors.json` against `node_dictionary.csv` first.
- **Execution modes are unvalidated.** The six D4 labels are shown per step, but SRC-007's target map draws one undifferentiated agentic band and tags nothing.
- **Only five relationships are drawn.** Four cross-scenario links exist in the source layer plus one early-start marker. Sequential adjacency between neighbouring processes is deliberately *not* drawn as a dependency, because the source does not establish one. The real dependency graph needs INP-B1 `Blocked_By` / `Blocks`.
- **The R03 Miro board work is unfinished and out of scope here.** See `analysis-output/2026-09-08-miro-journey-r03/MIRO_STATUS.md`. This session produced a local page; it did not touch the board.
- **Testing was structural, not visual-regression.** Layout, the panel, focus handling, keyboard escape, the scenario filter, deep links and image loading were verified programmatically in-browser. Screenshots covered the map, a rendered workflow and the references grid. There has been no accessibility audit, no cross-browser pass, no print proof, and no test at 200% zoom.
- **Two servers on localhost.** Nothing is deployed or shared. Both die on reboot.
- **The source workbook is outside the repo and has already moved.** `workbook.json` preserves its content, but the provenance chain currently points at a path that no longer resolves.

### Bugs found and fixed this session, worth knowing about

1. `.grid{overflow:hidden}` makes an element a scroll container, so `position:sticky` anchored to the grid instead of the viewport and the stage header covered the client ribbon by 65px. `overflow:clip` clips without creating a scroll container.
2. `requestAnimationFrame` is throttled to nothing while a page is hidden, so the SVG connectors never drew in a background tab. Now paired with a timeout, plus a `ResizeObserver` and image-load handlers.
3. A more specific CSS rule zeroed the auto margin on a heading that had inherited a `62ch` max-width, pinning it left inside a centred block.
