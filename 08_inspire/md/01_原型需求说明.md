# 从客户申请到交易就绪：原型需求说明

版本：Workshop 整理版 · 2026-09-09

## 1. 这个产品到底要解决什么

Clear to Trade 想解决的是：一个机构客户申请银行业务时，多个团队需要分别核对主体、材料、风险、协议及审批条件，但这些工作分散在不同系统和沟通渠道里。客户反复提供资料，员工反复追问进度，最后仍很难说清“这宗申请还差什么、谁负责下一步、什么时候可以确认就绪”。

原型的核心价值是让这些团队围绕同一个案件协作：看见一致的申请背景、明确的要求和证据、具体的未决事项，以及有依据的下一步。

**Workshop 要验证三个问题：这些痛点是否真实？哪些改进最值得先做？哪些判断必须由人负责？**

## 2. 用同一个案例理解整个旅程

澳大利亚的 **Entity A** 申请外汇远期业务。新加坡的 **Entity B** 是其申报母公司。**Person T** 任职于 B，并声称帮助 A 协调资料。

这里有三个必须分开的事实：

1. **谁是申请主体？** 是 A，不能因为 B 是母公司，就把 B 当成申请人。
2. **T 是谁？** 要核实其身份和关系；姓名相似的筛查命中需要进一步判断。
3. **T 可以做什么？** 提供信息、访问请求项目、代表 A 签署或交易，是不同的权限，需要各自的依据。

贯穿案例的示例：T 出现疑似筛查命中，复核人员发现缺少某项身份事实，于是发出限定范围的补件请求。T 提交资料后，团队先评估其是否充分，再回到原筛查任务。即使这个疑点已经解决，也不自动意味着法务、信贷、质量复核和整案准入都已通过。

该案例刻意保留未决项。它适合讨论“如何处理未知”，不能拿它演示一个没有依据的全绿结局。

## 3. 谁参与，各自为什么需要这个产品

| 角色 | 想完成的工作 | 希望得到的支持 |
| --- | --- | --- |
| 客户 / 信息提供者（T） | 理解请求并提供被允许提交的资料 | 清晰的问题、用途及剩余事项，不反复提交相同材料 |
| 客户经理 | 界定客户需求、协调沟通、传达结果 | 统一的客户背景与可对外说明的进度 |
| 案件经理 | 协调全案、识别阻塞与下一步 | 看见整体依赖和责任方；这是原型中的设计角色，真实职责待确认 |
| KYC 运营 | 确定要求、获取和核验证据、准备筛查 | 少查找、少重复录入，知道证据支持哪个用途 |
| 风险 / 合规专家 | 判断筛查命中、强化尽调及条件 | 可比较的事实、来源、未决问题和明确的审批依据 |
| QA 质量保证 | 检查充分性、发出具体整改并复审 | 对应到要求和证据版本的发现，而非让全案无差别重做 |
| 利益冲突控制 | 及早发现、调查及处理潜在冲突 | 可尽早启动的输入、明确的升级和结论 |
| 信贷 | 评估风险、限额和条件 | 可靠输入、审批记录及传给法务的当前条款 |
| 法务 | 准备、审查和签署适用协议 | 当前信贷条件、开放条款问题及签署权限依据 |

这些角色用于解释参与者体验，不等于已确定的银行岗位分工或权限配置。

## 4. 把 15 个场景讲成 5 个阶段

五个阶段是讲解顺序，不是强制串行流程。利益冲突从受理开始，法务和信贷按可用输入并行推进。质量问题或材料缺口可以形成返回复核的回路。

| 阶段 | 讲什么 | 关键产出 | 覆盖场景 | 当场讨论 |
| --- | --- | --- | --- | --- |
| ① 发起 | 谁提出申请、产品范围是什么、谁能代表谁 | 统一申请背景、明确的未知项 | SCOPE、ENTITY；M0–M1 | T 可以为 A 做什么，需要哪些依据？ |
| ② 确定要求 | 先确定适用要求，再复用证据，只追问剩余缺口 | 要求清单、证据用途评估、补件请求 | REQUIREMENTS、SOURCE、GAP、VALIDATE；M2–M3 | 哪些信息已经有了，哪些还缺，为什么要？ |
| ③ 评估风险 | 确认筛查范围、对比命中事实、按需强化尽调 | 有理由的结论、未决问题与条件 | POPULATION、MATCH、EDD；M4–M5 | 什么证据足以支持判断，哪些情况应转人工？ |
| ④ 协同解决 | 冲突、信贷、法务并行；QA 对具体问题复审 | 各条线结果、版本依赖、下一责任方 | CONFLICTS、CREDIT、LEGAL、QA；M7、C2、C1、M6 | 谁在等谁，哪些工作可以继续？ |
| ⑤ 确认就绪 | 汇总前提、由授权人员确认、独立记录和通知 | 限定范围的就绪判断、决定与发布记录 | READINESS、PUBLISH；M8 | 还差什么，谁能确认，通知失败怎么办？ |

### 不能因为页面简化而丢掉的业务关系

- **补件回路：** 筛查复核发现缺口 → 发出具体请求 → 评估提交材料 → 返回同一项复核。补件本身不替代裁定。
- **早期并行：** 受理信息可支持提前启动利益冲突检查，不需要等到第五阶段。
- **跨团队依赖：** 信贷向法务提供当前协议数据；条件版本发生变化，依赖该版本的工作需要重新检查。
- **最终汇合：** 就绪检查覆盖所有当前适用前提；未知或未解决事项不能静默算作通过。

## 5. 十组产品需求，用业务语言表达

下列十组对应原有 `CTT-REQ-001–010`。标题和解释作了通俗化整理，编号与关键验收边界沿用来源。它们仍是需求假设。

### R01 · 所有人围绕同一份申请背景工作

**业务需求：** 保留申请主体、产品、范围及版本，把未知的记账安排明确显示。范围变化后，后续工作能知道自己依据的是哪个版本。

**人负责：** 确认主体、业务范围及具体代表权限。

**验证例子：** A 申请外汇远期，T 任职于 B。记录申请后，交易对手仍是 A，T 不因此获得签署或交易权限。

对应 `CTT-REQ-001 / AC-F01`；场景 SCOPE、ENTITY。

### R02 · 说清楚要什么，以及为什么要

**业务需求：** 按当前范围维护适用要求，并区分“适用”“不适用”“尚未确认”。要求要有版本和依据。

**人负责：** 确认要求集和例外，而不是让系统把未知自动归为不适用。

**验证例子：** 一项要求的适用性未知时，页面仍显示待确认，它不能因此满足就绪条件。

对应 `CTT-REQ-002 / AC-F02`；场景 REQUIREMENTS。

### R03 · 资料收到与证据够用分别记录

**业务需求：** 复用材料时保留来源、版本和使用目的；同一材料对一个用途充分，不表示对所有用途都充分。

**人负责：** 记录证据充分性和理由。

**验证例子：** 已收到 T 的资料，但仍不足以证明代表权限，相关要求保持未满足。

对应 `CTT-REQ-003 / AC-F03`；场景 SOURCE、VALIDATE。

### R04 · 只向合适的人请求真正缺少的内容

**业务需求：** 把缺口变成明确、限定范围的请求。不同贡献者只能访问获准的项目，支持部分提交与独立复核。

**人负责：** 分别判断请求内容、派发、身份认证、访问权限和业务代表权限。

**验证例子：** 两个请求分给两个人，一人提交自己的项目后，只改变该项目的收取状态；另一项目和整案状态不跟着完成。

对应 `CTT-REQ-004 / AC-F04`；场景 GAP、VALIDATE。

### R05 · 对正确的对象筛查，并审慎判断疑似命中

**业务需求：** 将筛查对象、运行记录和结果关联起来，明确覆盖是否完整、是否过期，以及强化尽调是否适用。

**人负责：** 对重要发现作出处置；独立判断强化尽调适用性及审批条件。

**验证例子：** 筛查对象为空、过时或未经确认时，不能显示覆盖完整，也不能因此宣布就绪。

对应 `CTT-REQ-005 / AC-F05`；场景 POPULATION、MATCH、EDD。

### R06 · 可以并行的先做，必须等待的说清楚

**业务需求：** 显示专业条线之间真正依赖的输入和版本，允许有独立前提的准备工作继续。

**人负责：** 专业判断、批准与签署分别记录。

**验证例子：** 法务已引用某版信贷条款，随后条款改变；系统应提示旧版本失效，并在复核前阻止相关签署与就绪。

对应 `CTT-REQ-006 / AC-F06`；场景 CONFLICTS、CREDIT、LEGAL。

### R07 · 重要决定由有权限的人明确作出

**业务需求：** 记录准入决定前检查当前范围、就绪依据和操作权限，要求明确确认。

**人负责：** 按真实银行确定的权限作出决定；原型中的演示权限不构成真实授权。

**验证例子：** 案件已达到“待授权确认”，但未经配置授权的 QA、客户经理或未知角色尝试确认时，不能产生准入决定。

对应 `CTT-REQ-007 / AC-F07`；场景 ENTITY、READINESS。

### R08 · 变化影响哪些工作，要能够解释

**业务需求：** 某条线暂停、材料变化或要求变化时，指出具体受影响的要求、证据用途和下游依赖。

**人负责：** 明确暂停责任人与恢复依据。

**验证例子：** 一项问题暂停法务工作时，系统说明影响范围；其他工作是否可继续必须有依据，不能因为没有画依赖线就认定不受影响。

对应 `CTT-REQ-008 / AC-F08`；场景 CONFLICTS、LEGAL、QA。

### R09 · 就绪、确认、发布是三件事

**业务需求：** 汇总全部当前适用前提后，先得到就绪判断；授权确认形成决定；发布通知是独立操作。

**人负责：** QA 完成自己的签核，获授权人员确认准入，客户经理按已记录结果沟通。

**验证例子：** 所有前提满足但还没有授权确认时，只能是“待授权确认”。确认后通知失败，保留原决定并处理通知失败，不能重复审批或执行交易。

对应 `CTT-REQ-009 / AC-F09`；场景 QA、READINESS、PUBLISH。

### R10 · 切换视图不能改写业务历史

**业务需求：** 场景、产品、语言、打印和返回之间切换时保留已保存的业务版本与阅读位置。

**人负责：** 明确区分阅读操作与业务决定。

**验证例子：** 在工作已保存的情况下换语言、返回故事或打印，只改变展示，不生成审批或覆盖业务决定。

对应 `CTT-REQ-010 / AC-F10`；跨场景需求。

## 6. AI 应该出现在哪里

| 工作 | 适合讨论的辅助方式 | 保留的人工边界 |
| --- | --- | --- |
| 整理申请 | 提取关键信息、提示可能重复的案件 | 人确认主体和范围，不静默合并案件 |
| 确定要求 | 根据已配置规则提出要求与待确认项 | 人处理未知、解释与例外 |
| 获取证据 | 找到材料、注明来源、归纳缺口 | 人判断用途和充分性 |
| 筛查复核 | 对齐事实、呈现差异、准备补件请求 | 人裁定重要命中与风险结论 |
| 跨团队协同 | 跟踪当前依赖、提示版本变化 | 人决定暂停、恢复、批准与签署 |
| 就绪解释 | 汇总前提、解释还差什么 | 有权限的人作出最终决定 |

原型中的 Rule、Workflow、Deterministic Skill、Semantic Skill、Bounded Agent candidate 等细分术语适合会后技术分解。主 workshop 只需讲清“产品可以帮助准备什么”和“人必须判断什么”。**并非所有自动化都需要智能体。**

## 7. 先讨论什么，不必一次决定所有实现

建议用“筛查疑点 → 精准补件 → 按用途复核 → 回到原任务”作为候选小范围试点，因为它贯穿一个明确问题、一次客户互动和一次人工判断。此选择是本次整理建议，不是原目录中的 MVP 排名；原需求目录的优先级和评分字段尚未填写。

| Workshop 需要形成的结果 | 示例 |
| --- | --- |
| 一个具体痛点 | 为澄清同一个身份疑点，多团队反复索取信息 |
| 一个候选试点范围 | 先做 MATCH–GAP–VALIDATE 的闭环 |
| 一个清楚的人机边界 | 系统准备对比和请求，专家作出裁定 |
| 一个验证方法 | 用脱敏样本回放，记录重复请求次数、等待时间、追溯完整性 |
| 一个跟进责任与期限 | 指定业务联系人核实授权规则，给出日期；由参会者填写 |

指标这里只提出测量方法，不设置虚构基线、不承诺效率提升比例。范围、数据可用性、集成成本和控制责任均须后续验证。

## 8. 会后必须补齐的问题

1. 哪些岗位可以确认范围、接受证据、批准风险结论和确认准入？现有权限模型能否支持？
2. 适用要求由谁维护，哪些规则可以明确配置，哪些必须留给专家？
3. 现有案件、资料库、筛查、信贷和法务系统，分别能提供哪些数据与接口？
4. 何种资料可跨用途复用？有效期、来源和权限要求如何体现？
5. 哪些变化触发局部重审，哪些触发全案重审？
6. 对“已收到、已接受、单项通过、全案就绪、已确认、已发布”的业务定义是否一致？
7. 选择哪个可控样本集和流程片段来验证真实痛点与效果？
